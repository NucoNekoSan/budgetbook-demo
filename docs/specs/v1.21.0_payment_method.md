# v1.21.0 支払手段マスタ導入

## 目的

クレジットカード、電子マネー、現金、銀行引落などの支払手段を、会計上の `Account` だけで表現し続けると、利用日ベースの支出分析と引落日ベースの資金繰りが混ざりやすい。
将来のカード別利用額、引落予定額、固定費検出、支払手段別分析に備え、支払手段マスタを導入する。

## 判断

**`PaymentMethod` モデルを採用し、v1.21.0 として実装済み。ただし、`Account` / `Transfer` は置き換えない。**

`PaymentMethod` は入力・分析・引落予定の補助軸とし、会計残高の正本は引き続き `Account` / `Transaction` / `Transfer` で管理する。

## 現状維持するもの

| 既存要素 | 維持理由 |
|---|---|
| `Transaction.account` | その取引で残高が動く会計口座。残高計算・月次締め・照合の正本 |
| `Account.kind=LIABILITY` | クレジットカード未払い・ローンなどを B/S 上の負債として表現できる |
| `Transfer` | 銀行口座からカード負債口座への引落・返済を収入/支出に混ぜず記録できる |
| `LoanProfile` | 有利子負債の利息・元金返済自動化は既存責務として維持 |

## 設計方針

### ① 支払手段は会計口座ではない

`PaymentMethod` は「どう支払ったか」を表す。
`Account` は「どの残高が動いたか」を表す。

例:

| 利用日 | 支払手段 | `Transaction.account` | 引落元 | 引落表現 |
|---|---|---|---|---|
| 2026-05-10 | クレジットカードA | カードA負債口座 | 銀行A | 2026-06-27 に `Transfer(銀行A → カードA負債口座)` |
| 2026-05-10 | 現金 | 現金口座 | なし | Transaction のみ |
| 2026-05-10 | デビットカード | 普通預金口座 | なし | Transaction のみ |
| 2026-05-10 | 電子マネー | 電子マネー口座 | チャージ元口座 | チャージを `Transfer`、利用を `Transaction` |

### ② クレジットカードは負債口座として残す

クレジットカードを `PaymentMethod` だけで表すと、未払残高、照合、返済、B/S が弱くなる。
そのため、カード利用を本格管理する場合は以下を推奨する。

- `Account(kind=LIABILITY)` にカード未払口座を作る
- カード利用取引は `Transaction.account = カード負債口座`
- 引落は `Transfer(from=銀行口座, to=カード負債口座)`
- `PaymentMethod` はその取引の支払手段ラベルとして `Transaction.payment_method` に紐付ける

カードを負債口座化せず、銀行口座や現金口座に直接 expense 計上する簡易運用も禁止しない。
その場合も `PaymentMethod` だけを任意設定できる。

### ③ 既存データは自動変換しない

初回 migration で既存取引から `PaymentMethod` を自動推定しない。

理由:

- `description` や `account.name` だけでは支払手段を正確に推定できない
- 誤推定は資金繰り・カード利用額の分析を壊す
- `payment_method=NULL` でも既存機能は維持できる
- 締め済み月の既存取引を data migration で更新しない方が安全

## 想定データモデル

### `PaymentMethod`

```python
class PaymentMethod(TimeStampedModel):
    class Kind(models.TextChoices):
        CASH = 'cash', '現金'
        BANK = 'bank', '銀行口座'
        CREDIT_CARD = 'credit_card', 'クレジットカード'
        DEBIT_CARD = 'debit_card', 'デビットカード'
        ELECTRONIC_MONEY = 'electronic_money', '電子マネー'
        QR = 'qr', 'QR決済'
        OTHER = 'other', 'その他'

    name = models.CharField('支払手段名', max_length=100, unique=True)
    kind = models.CharField('種別', max_length=30, choices=Kind.choices, db_index=True)
    account = models.ForeignKey(
        'Account',
        on_delete=models.PROTECT,
        null=True,
        blank=True,
        related_name='payment_methods',
        verbose_name='通常利用口座',
        help_text='この支払手段で通常残高が動く口座。クレジットカードなら負債口座。',
    )
    settlement_account = models.ForeignKey(
        'Account',
        on_delete=models.PROTECT,
        null=True,
        blank=True,
        related_name='settlement_payment_methods',
        verbose_name='引落元口座',
        help_text='クレジットカード等の引落元となる資産口座。',
    )
    closing_day = models.PositiveSmallIntegerField('締日', default=0)
    settlement_day = models.PositiveSmallIntegerField('引落日', default=0)
    is_active = models.BooleanField('有効', default=True)
    notes = models.TextField('メモ', blank=True)

    class Meta:
        verbose_name = '支払手段'
        verbose_name_plural = '支払手段'
        ordering = ['name']
```

`closing_day` / `settlement_day` は 0〜31 とする。
0 は未設定。31 は月末扱い候補とし、実装時に日付解決ルールを明記する。

### `Transaction.payment_method`

```python
payment_method = models.ForeignKey(
    PaymentMethod,
    on_delete=models.PROTECT,
    null=True,
    blank=True,
    related_name='transactions',
    verbose_name='支払手段',
)
```

nullable とする。既存取引と日常入力速度を守るため、必須化しない。

## Validation 方針

`PaymentMethod.kind` ごとの制約:

| 種別 | `account` | `settlement_account` |
|---|---|---|
| 現金 | 資産口座推奨 | 空 |
| 銀行口座 | 資産口座推奨 | 空 |
| デビットカード | 資産口座推奨 | 空 |
| クレジットカード | 負債口座推奨 | 資産口座推奨 |
| 電子マネー | 資産口座推奨 | 任意 |
| QR決済 | 資産口座または負債口座 | 任意 |

初期実装では「推奨」をUIヘルプと warning に留め、保存拒否は最小限にする。
ただし `settlement_account` に負債口座を指定することは拒否する。

## UI 方針

### 取引フォーム

- `payment_method` は任意
- 選択時に `account` を自動提案できるが、強制変更はしない
- `Transaction.account` はユーザーが最終確認する
- 支払手段未設定でも保存できる

日常入力の負荷を上げないため、初期導入では「支払手段を選ばないと保存できない」は採用しない。

### 支払手段管理画面

設定画面に以下を追加する。

- 支払手段一覧
- 追加
- 編集
- 有効/無効切替
- 参照口座・引落元口座・締日・引落日の表示

削除は原則不要。使用済み支払手段は `is_active=False` で候補から外す。

## 引落予定の扱い

初期導入では引落予定 `Transfer` の自動生成はしない。

理由:

- カード会社ごとの締日・引落日・休日補正が異なる
- 分割払い・リボ・返品・キャンセルが絡むと誤生成リスクが高い
- 既存の `LoanProfile` / `accrue_loan_principal` と責務が重なる

v1.21.0 初期スコープは以下まで。

- 支払手段別利用額の集計
- クレジットカード別の利用額確認
- 引落元口座・締日・引落日のメモ的管理

引落予定生成は別Issueで検討する。

## `LoanProfile` との境界

`LoanProfile` は有利子負債の返済計画・利息計算を扱う。
`PaymentMethod` は支払手段と引落予定情報を扱う。

| 論点 | `LoanProfile` | `PaymentMethod` |
|---|---|---|
| 対象 | 有利子負債・ローン・リボ | 支払方法全般 |
| 利息計算 | あり | なし |
| 元金返済Transfer自動化 | あり | 初期導入ではなし |
| 日常取引入力 | 直接使わない | 任意選択候補 |
| B/S | 負債口座を通じて反映 | 直接反映しない |

クレジットカードのリボ残高を本格管理する場合は、`Account(kind=LIABILITY)` + `LoanProfile` + `PaymentMethod(kind=CREDIT_CARD)` を併用する。

## CSV import/export 方針

### import

初期導入では既存CSVフォーマットを維持する。
`支払手段` 列が存在する場合だけ任意で解釈する。

| CSV列 | 挙動 |
|---|---|
| なし | `payment_method=NULL` |
| `支払手段` が既存名と完全一致 | `payment_method` を紐付け |
| 不一致 | preview で警告し、取り込み時は `payment_method=NULL` |

### export

後方互換のため既存列は維持する。
`支払手段` 列追加は既存利用者への影響を確認してから行う。
必要なら「拡張CSV」として別URL/パラメータに分ける。

## Migration 計画

初期 migration は追加のみ。

1. `PaymentMethod` 新規テーブル追加
2. `Transaction.payment_method` nullable FK 追加
3. 既存データ移行なし

禁止事項:

- 既存 `Account` の自動変換
- 既存 `Transaction.account` の自動変更
- 既存 `Transfer` の自動生成
- 締め済み月の既存取引更新

## ロールバック方針

実装前に本番DBバックアップを取得する。

ロールバック時:

1. v1.21.0 migration を rollback
2. `Transaction.payment_method` カラムと `PaymentMethod` テーブルが削除される
3. 既存 `Transaction.account` / `description` / `category` / `Transfer` は残る
4. 支払手段マスタに登録した情報は失われるため、必要なら事前にCSV exportする

## セキュリティ・個人情報

支払手段名にはカード会社名、銀行名、個人運用メモが含まれる可能性がある。

- 実カード名・実口座名をpublic docsやdemo seedに入れない
- `.env` / DB / backup と同じく個人金融情報として扱う
- CSV export 時は支払手段名にも CSV injection 対策を適用する
- 監査ログに支払手段名を残す場合は個人情報として扱う

## テスト計画

実装時に最低限追加するテスト:

- `PaymentMethod` 作成・編集・無効化
- `settlement_account` に負債口座を指定した場合の拒否
- `Transaction.payment_method=NULL` の既存互換
- 取引作成/編集で任意の支払手段を設定できる
- 支払手段無効化後も既存取引表示が壊れない
- 支払手段別集計で `payment_method=NULL` を未設定として扱う
- CSV import の `支払手段` 列なし既存互換
- CSV injection 対策が支払手段名にも効く
- 月次締め済み月の既存取引が data migration で変更されない
- `LoanProfile` / 元金返済 Transfer 自動化の既存テストが影響を受けない

## 非対象

- カード明細の自動取込
- 銀行API連携
- 自動引落予定 `Transfer` 生成
- 分割払い・リボ払いのカード明細単位管理
- 休日補正込みの引落日計算
- 既存データの一括自動補正

## 受け入れ条件

完了条件:

- `PaymentMethod` 採用判断が記録されている
- `Account` / `Transfer` / `LoanProfile` との境界が明確である
- 既存データを自動変換しない方針が明記されている
- migration / ロールバック / セキュリティ影響が明記されている
- `PaymentMethod` / `Transaction.payment_method` が追加されている
- 取引フォーム、設定画面、CSV import任意列が支払手段に対応している
