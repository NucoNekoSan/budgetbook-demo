# v1.20.0 支払先マスタ導入

## 目的

取引の `description` だけに支払先・店名を入れ続けると、同じ支払先でも表記揺れが蓄積し、長期分析の精度が落ちる。
将来の支払先別支出分析、固定費検出、CSV import の名寄せ、自動カテゴリ推定に備え、支払先マスタを導入する。

## 判断

**採用し、v1.20.0 として実装済み。**

モデル名は `Payee` を採用する。

| 候補 | 判断 | 理由 |
|---|---|---|
| `Payee` | 採用 | 店舗、医療機関、保険会社、給与支払者、個人支払先を広く表せる |
| `Store` | 不採用 | 店舗に寄りすぎ、病院・薬局・自治体・保険会社に合わない |
| `Merchant` | 不採用 | 決済事業者寄りで、家計簿上の受診先・給与支払者を含めにくい |

## 設計方針

### ① `description` は残す

`Transaction.description` は廃止しない。役割を以下に分ける。

| 項目 | 役割 |
|---|---|
| `Transaction.description` | レシート・明細から入る自由入力の摘要。既存CSV、検索、一覧表示の互換性を維持する |
| `Transaction.payee` | 分析用に正規化された支払先・入金元。任意入力の nullable FK |
| `Transaction.memo` | 補足説明、購入内訳、個人的なメモ |

既存のCSV export/import、検索、一覧表示は `description` を主表示として維持し、`payee` は分析軸として追加する。

### ② 既存データは自動変換しない

初回 migration で既存 `Transaction.description` から `Payee` を自動生成しない。
理由は以下。

- 表記揺れの自動名寄せは誤統合リスクがある
- 個人金融データで誤分類すると分析結果の信頼性が落ちる
- 既存取引は `payee=NULL` でも全機能が動く
- ロールバック時の影響を最小化できる

必要になった時点で、別途 dry-run 付き管理コマンドを検討する。

### ③ `Payee` は無効化運用にする

使用済み `Payee` は削除ではなく `is_active=False` で新規入力候補から外す。
過去分析の軸を壊さないため、参照中の `Payee` は物理削除しない。

## 想定データモデル

### `Payee`

```python
class Payee(TimeStampedModel):
    name = models.CharField('支払先名', max_length=120, unique=True)
    normalized_name = models.CharField('正規化名', max_length=120, unique=True)
    is_active = models.BooleanField('有効', default=True)
    notes = models.TextField('メモ', blank=True)

    class Meta:
        verbose_name = '支払先'
        verbose_name_plural = '支払先'
        ordering = ['name']
```

`normalized_name` は、前後空白、全角/半角、連続空白、英字大小などを正規化した比較用文字列とする。
正規化ルールは migration ではなくモデル/Form/service 層で一元化する。

### `PayeeAlias`

```python
class PayeeAlias(TimeStampedModel):
    payee = models.ForeignKey(
        Payee,
        on_delete=models.CASCADE,
        related_name='aliases',
        verbose_name='支払先',
    )
    alias = models.CharField('別名', max_length=120, unique=True)
    normalized_alias = models.CharField('正規化別名', max_length=120, unique=True)

    class Meta:
        verbose_name = '支払先別名'
        verbose_name_plural = '支払先別名'
        ordering = ['alias']
```

別名例:

| `Payee.name` | `PayeeAlias.alias` |
|---|---|
| 店舗A | 店舗A 支店、SHOP-A |
| 通販A | 通販A 明細、ONLINE-A |
| 医療機関A | 医療機関A 受付、薬局A |

### `Transaction.payee`

```python
payee = models.ForeignKey(
    Payee,
    on_delete=models.PROTECT,
    null=True,
    blank=True,
    related_name='transactions',
    verbose_name='支払先',
)
```

`on_delete=PROTECT` とする。支払先を削除して過去分析軸を失う事故を避けるため。
削除したい場合は `is_active=False` を使う。

## UI 方針

### 取引フォーム

初期導入では入力負荷を増やさない。

- `description` はこれまで通り必須
- `payee` は任意
- 既存 `Payee` から任意選択
- 候補がない場合でも保存可能
- 新規 `Payee` 作成は最初から強制しない

入力UIは既存 `Payee` の選択を基本とする。
候補選択を必須にすると、日常入力の速度が落ちるため採用しない。
`description` 入力値からのリアルタイムサジェストは初期実装では行わず、必要なら別Issueで検討する。

### 支払先管理画面

初期導入で必要な最小機能:

- 支払先一覧
- 追加
- 編集
- 無効化
- 別名追加/削除
- 参照件数表示

物理削除は原則不要。未使用レコードだけ削除可能にする場合も、誤削除防止の確認と監査ログを必須にする。

## CSV import 方針

CSV import では、`description` から `PayeeAlias.normalized_alias` / `Payee.normalized_name` を照合し、preview で候補表示する。

初期導入では `Payee` の自動新規作成はしない。

| 状態 | 挙動 |
|---|---|
| 完全一致 1 件 | preview で候補表示し、import 時に紐付け |
| 複数候補 | 正規化一意制約により発生しない前提。発生時は `payee=NULL` のまま取り込み |
| 候補なし | `payee=NULL` のまま取り込み |

CSV export は後方互換のため既存列を維持し、必要なら `支払先` 列追加版を別途検討する。

## 医療費・保険料との境界

`MedicalExpense.provider` は v1.20.0 初期導入では変更しない。
医療機関・薬局も支払先の一種だが、税控除機能は国税庁様式の列名と既存CSV互換が重要なため、まずは `Transaction.payee` のみを対象にする。

将来、必要であれば `MedicalExpense.payee` nullable FK を別Issueで検討する。

`InsurancePremium.insurer` も同様に、保険料控除証明書上の保険会社名として維持する。

## Migration 計画

初期 migration は追加のみ。

1. `Payee` 新規テーブル追加
2. `PayeeAlias` 新規テーブル追加
3. `Transaction.payee` nullable FK 追加
4. 既存データ移行なし

禁止事項:

- 既存 `Transaction.description` の削除
- 既存 `description` からの自動 `Payee` 一括生成
- 締め済み月の既存取引を自動更新する data migration

## ロールバック方針

実装前に本番DBバックアップを取得する。

ロールバック時:

1. v1.20.0 migration を rollback
2. `Transaction.payee` カラム、`Payee`、`PayeeAlias` が削除される
3. 既存 `Transaction.description` / `memo` / `category` / `account` は残る
4. 支払先マスタに登録した新規情報は失われるため、必要なら事前にCSV exportする

## セキュリティ・個人情報

`Payee` は個人名、医療機関名、勤務先名を含み得るため、個人金融情報と同等に扱う。

- Git 管理対象に実データを含めない
- demo seed に実名支払先を入れない
- CSV export 時は既存の CSV injection 対策を適用する
- 監査ログには支払先名を残す場合があるため、ログも個人情報として扱う

## テスト計画

実装時に最低限追加するテスト:

- `Payee` / `PayeeAlias` の正規化一意制約
- 使用中 `Payee` の物理削除が保護される
- `is_active=False` が新規入力候補から除外される
- `Transaction.payee=NULL` の既存互換
- 取引作成/編集で `payee` を任意設定できる
- CSV import preview で別名一致候補が表示される
- CSV injection 対策が `Payee.name` にも効く
- 支払先別集計で `payee=NULL` は `description` 集計と混同しない
- 月次締め済み月の既存取引が data migration で変更されない

## 非対象

- AI自動分類
- 銀行API/カード明細API連携
- 過去データの強制一括補正
- `MedicalExpense.provider` / `InsurancePremium.insurer` の同時FK化
- 複雑な法人番号・店舗コード管理

## 受け入れ条件

完了条件:

- `Payee` 採用判断が記録されている
- `description` との役割分担が明確である
- 既存データを自動変換しない方針が明記されている
- migration / ロールバック / セキュリティ影響が明記されている
- `Payee` / `PayeeAlias` / `Transaction.payee` が追加されている
- 取引フォーム、設定画面、CSV import preview が支払先に対応している
