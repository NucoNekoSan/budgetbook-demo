# v1.22.0 カテゴリ履歴と再分類ポリシー

## 目的

家計簿を長期運用すると、カテゴリ名や分類方針を変えたくなる。
単純に `Category.name` / `kind` / `section` / `tax_tag` を変更すると、過去の取引表示・レポート・税控除タグ集計の意味が後から変わる。

カテゴリ変更時の過去データ扱いを明文化し、再分類操作と通常のカテゴリ編集を分離する。

## 判断

**カテゴリ履歴を採用し、v1.22.0 として実装済み。ただし、初期導入では複雑な会計科目体系や多段カテゴリ階層は導入しない。**

設計上の方針:

- `Category` は現在のカテゴリマスタとして維持する
- 名前変更・分類変更は `CategoryChangeLog` に履歴を残す
- 過去取引のカテゴリ付け替えは通常編集ではなく「再分類」操作として扱う
- 締め済み月の自動再分類はしない
- 月次締めスナップショットは金額の正本であり、カテゴリ内訳の完全スナップショットまでは初期導入しない

## 既存仕様の整理

現状の `Transaction.category` は `Category` への FK。
そのため、`Category.name` を変更すると、過去取引の表示名も新しい名前で表示される。

これは短期運用では問題ないが、以下の場面で意味が揺れる。

- 「外食」を「食費」に統合した後、過去の外食支出を区別できなくなる
- `tax_tag` を後から付け替えた場合、過去の税控除レポート対象が変わる
- `section` を変更した場合、過去の支出構成/予算比の意味が変わる
- 月次締め済み月の現在集計と締め時点の分類が一致しなくなる

## 用語定義

| 用語 | 定義 |
|---|---|
| カテゴリ編集 | `Category` 自体の名前・分類・税控除タグ等を変更すること |
| 再分類 | 既存 `Transaction.category` を別カテゴリへ付け替えること |
| 履歴 | カテゴリ編集または再分類の前後値・理由・操作ユーザーを記録したもの |
| 当時カテゴリ | 取引作成時または締め時点でのカテゴリ名・分類 |
| 現在カテゴリ | 現在の `Category` マスタ上の名前・分類 |

## ポリシー

### ① カテゴリ名変更は過去表示にも反映される

初期導入では `Transaction` にカテゴリ名スナップショットを持たせない。
したがって、カテゴリ名変更は過去取引の表示にも反映される。

ただし、変更履歴に旧名・新名を残す。
これにより「いつ、なぜ、誰が、カテゴリ名を変えたか」を追跡できる。

理由:

- 既存UI・CSV・集計互換を維持できる
- `Transaction` への大規模な履歴カラム追加を避けられる
- 日常運用では「カテゴリ名の誤字修正」「分かりやすい名前への変更」は過去にも反映した方が自然

### ② `kind` 変更は原則禁止する

`Category.kind` は収入/支出の会計意味を決める。
取引で使用済みのカテゴリについて `kind` を変更すると、過去の収入・支出合計が変わる。

方針:

- 未使用カテゴリの `kind` 変更は許可
- 使用済みカテゴリの `kind` 変更は拒否
- 収入カテゴリを支出カテゴリへ変えたい場合は、新カテゴリを作成し、必要な取引を明示的に再分類する

### ③ `section` / `tax_tag` 変更は許可するが履歴必須

`section` と `tax_tag` は分析・税控除レポートに影響する。
変更自体は許可するが、変更履歴と監査ログを必須にする。

注意:

- 過去レポートも現在の `section` / `tax_tag` で再集計される
- 税控除レポートは参考計算であり、申告済み年度の再集計値が変わり得る
- 締め済み月の金額スナップショットは変わらないが、カテゴリ別分析は変わり得る

### ④ 再分類は明示操作にする

過去取引の `category` を付け替える操作は、通常のカテゴリ編集とは別に扱う。

再分類操作では以下を必須にする。

- 対象期間
- 変更前カテゴリ
- 変更後カテゴリ
- 対象件数
- 締め済み月を含むか
- 理由
- dry-run 表示
- 明示確認
- AuditLog

締め済み月を含む再分類は初期導入では拒否する。
必要になった場合は、締め取消 → 再分類 → 再締めを手順化する。

## 想定データモデル

### `CategoryChangeLog`

```python
class CategoryChangeLog(TimeStampedModel):
    class Action(models.TextChoices):
        UPDATE = 'update', 'カテゴリ編集'
        RECLASSIFY = 'reclassify', '取引再分類'
        DEACTIVATE = 'deactivate', '無効化'
        REACTIVATE = 'reactivate', '有効化'

    category = models.ForeignKey(
        Category,
        on_delete=models.PROTECT,
        related_name='change_logs',
        verbose_name='対象カテゴリ',
    )
    action = models.CharField('操作', max_length=20, choices=Action.choices, db_index=True)
    before = models.JSONField('変更前', default=dict, blank=True)
    after = models.JSONField('変更後', default=dict, blank=True)
    affected_transaction_count = models.PositiveIntegerField('対象取引数', default=0)
    includes_closed_month = models.BooleanField('締め済み月を含む', default=False)
    reason = models.TextField('理由', blank=True)
    changed_by = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.SET_NULL,
        null=True,
        blank=True,
        verbose_name='操作ユーザー',
    )
```

`before` / `after` には以下を入れる。

```json
{
  "name": "食費",
  "kind": "expense",
  "section": "food",
  "tax_tag": "none",
  "is_active": true
}
```

再分類の場合は、対象期間・変更前後カテゴリID・件数を入れる。

### `CategorySnapshot` は初期導入しない

`Transaction` ごとにカテゴリ名スナップショットを持つ案は見送る。

理由:

- 全取引の表示・CSV・集計で「現在カテゴリ」と「当時カテゴリ」の使い分けが必要になり、UI複雑度が上がる
- 既存集計を大きく変更する必要がある
- 月次締めはすでに金額スナップショットを持っており、金額整合性は守られている

将来必要になった場合は、`Transaction.category_name_snapshot` ではなく、月次/年次レポート単位のカテゴリ内訳スナップショットを検討する。

## UI 方針

### カテゴリ編集

カテゴリ編集画面に注意表示を追加する。

- 名前変更は過去取引の表示にも反映される
- 使用済みカテゴリの `kind` 変更は不可
- `section` / `tax_tag` 変更は過去レポートの分類に影響する
- 変更理由の入力欄を追加するか検討

### 再分類画面

初期導入では一括再分類UIは作らない。
dry-run / apply のサービスを実装し、必要になったら専用画面または management command として別Issueで公開する。

推奨UI:

1. 変更前カテゴリを選択
2. 変更後カテゴリを選択
3. 対象期間を指定
4. dry-run で対象件数と締め済み月有無を表示
5. 締め済み月を含む場合は実行不可
6. 理由入力
7. 確認後に実行

## CSV import/export 方針

### import

CSV import は引き続きカテゴリ名完全一致を基本とする。

- 無効カテゴリは候補外
- 旧カテゴリ名・履歴名での自動解決は初期導入ではしない
- 履歴名での候補提示が必要なら `CategoryAlias` を別Issueで検討する

### export

既存CSV互換を維持し、現在の `Category.name` を出力する。
当時カテゴリ名の出力は初期導入では行わない。

## 月次締めとの関係

月次締めは以下をスナップショットとして保持している。

- 月初繰越
- 収入
- 支出
- 当月収支
- 月末残高
- 口座別残高

カテゴリ別内訳はスナップショットしていない。
そのため、カテゴリ変更で締め済み月の金額自体は変わらないが、カテゴリ別レポートの見え方は変わる。

方針:

- 締め済み月の `Transaction.category` 一括変更は初期導入では拒否
- `Category.name` / `section` / `tax_tag` 変更は許可するが履歴を残す
- 締め済み月の分類意味を厳密に固定したい場合は、将来 `MonthlyCategorySnapshot` を検討する

## Migration 計画

初期 migration は追加のみ。

1. `CategoryChangeLog` 新規テーブル追加
2. 既存 `Category` / `Transaction` へのカラム追加なし
3. 既存データ移行なし

禁止事項:

- 既存 `Transaction.category` の自動更新
- 既存 `Category.kind` の一括変更
- 締め済み月の自動再集計
- カテゴリ名スナップショットの全取引追加

## ロールバック方針

実装前に本番DBバックアップを取得する。

ロールバック時:

1. v1.22.0 migration を rollback
2. `CategoryChangeLog` テーブルが削除される
3. 既存 `Category` / `Transaction` / `MonthlyClosing` は残る
4. 履歴情報は失われるため、必要なら事前にCSV exportする

## セキュリティ・監査

カテゴリ名そのものは通常は機微性が低いが、医療・債務・収入源などを示す名前になり得る。

- 実カテゴリ名をpublic docsやdemo seedに入れない
- 変更理由に個人情報を書きすぎない
- `CategoryChangeLog` と `AuditLog` は個人金融情報として扱う
- CSV export 時はカテゴリ名にも既存のCSV injection対策を適用する

## テスト計画

実装時に最低限追加するテスト:

- カテゴリ編集時に `CategoryChangeLog` が作成される
- 使用済みカテゴリの `kind` 変更が拒否される
- 未使用カテゴリの `kind` 変更は許可される
- `section` / `tax_tag` 変更は履歴に before/after が残る
- カテゴリ無効化/有効化が履歴に残る
- 再分類 dry-run が対象件数を返す
- 締め済み月を含む再分類が拒否される
- 締め未済期間の再分類が AuditLog と CategoryChangeLog に残る
- CSV import は履歴名で自動解決しない
- 既存月次締め金額スナップショットがカテゴリ編集で変わらない

## 非対象

- 複雑な会計科目体系
- 多段カテゴリ階層
- `CategoryAlias`
- `MonthlyCategorySnapshot`
- 締め済み月の自動再分類
- 過去レポートの完全な当時カテゴリ再現

## 受け入れ条件

完了条件:

- カテゴリ名変更が過去表示にも反映される方針が明記されている
- 使用済みカテゴリの `kind` 変更禁止方針が明記されている
- `section` / `tax_tag` 変更の履歴必須方針が明記されている
- 再分類操作を通常編集と分離する方針が明記されている
- 月次締め済み月への影響と非対象が明記されている
- `CategoryChangeLog` が追加され、カテゴリ編集・無効化・再分類が履歴化されている
- 使用済みカテゴリの `kind` 変更が拒否され、未使用カテゴリの `kind` 変更は許可されている
- 再分類サービスが dry-run、理由必須、AuditLog、締め済み月拒否に対応している
